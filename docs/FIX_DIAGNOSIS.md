# Fix diagnosis: schema v2

This diagnosis is based on the generators, raw SQLite records, and the
`OAI.TotientFibers` source in `lean_files/finite_fiber.lean`. The files under
`out/FiniteFiber*/` are already schema v2; they are useful as a pre-change
snapshot but cannot serve as the schema v1 regression artifacts requested in
the original task. The pre-change measurements in that task are therefore the
only schema v1 baseline available in this checkout.

## Declaration DAG

| Requirement | Cause in the pre-fix implementation | Regression evidence |
|---|---|---|
| D1 auxiliary folding | `DeclarationDAG._is_auxiliary_name` only inspected name suffixes. `add_project_declarations` skipped folded records before transferring their outgoing refs, did not populate `aux_claims`, and did not retain an explicit raw-to-folded map. Pass A exported `is_matcher: false` for every declaration and used `isAuxRecursor` as the entire `is_auxiliary` test. | A fixture with `_proof_1`, `.eq_1`, and a dependency on each auxiliary must keep the original records in SQLite, expose the parent claims, and re-home dependencies with `via_aux:` evidence. |
| D2 source ranges | Pass A does use `findDeclarationRanges?`, but `cli._analyze_one` still creates regex-derived declaration ranges when Lean returned none. The fallback covers only theorem/lemma source and uses the next declaration line rather than Lean's full source range. It can therefore produce incomplete or overlapping ranges. | Validate Lean ranges against source bounds and pairwise non-overlap; test definitions and equation auxiliaries. |
| D3 external metadata | Pass A cached kind/module/type pretty/docstring for referenced constants, but did not export class/projection/autogenerated flags or a raw expression payload. The `type_expr_id` assigned by `DeclarationDAG` was fabricated from a name and did not point into `expr_node`. | External references must resolve to one metadata-bearing node and a real raw type expression record. |
| D4 roles and profiles | `DeclarationDAG.write` omitted `profile: "full"` and emitted only the narrative profile. Role classification fell through to `unknown`; the YAML contained only a few infrastructure prefixes. There was no aggregation of tactics or namespace-derived `automation_summary`. | Check full/narrative schemas and profile labels; test each role and automation summary without project-specific names. |
| D5 use kinds and edge provenance | `PassA.collectRefs` labelled every constant `applied_head`. The exporter called declaration values `value`; the DAG checked for `body` or kinds `def`/`instance`, although Lean exports `defn`, so definition-body refs became `proof_uses`. Statement refs were collected, but application arguments and type-only occurrences were not distinguished. | A definition calling another definition must create `body_uses`; statement constants must create `type_uses`; function heads and arguments need distinct `usage_kind`. |
| D6 readable type expressions | `exprPretty` used the legacy printer without an explicit user-facing configuration/context. Pretty output was also the only stored type representation; fabricated `type_expr_id` values did not identify raw expressions. | Compare rendered output to source-level notation and verify raw types remain separately addressable. |

## Proof claim graph

| Requirement | Cause in the pre-fix implementation | Regression evidence |
|---|---|---|
| P1 proof dataflow | `ProofClaimGraph.used_consts` preferred pretty assignment text and fell back to regexes. It did not receive an expression-level fragment with nested metavariable holes, so parent and child steps could inherit the same dependencies. | Compare step refs/fvars to expression-level references from each assignment. |
| P2 nesting | Inference depth defaulted to `1`; `scope_id` defaulted to `root`; `parent_inference` was read from payloads that Pass B never emitted. No `contains` hierarchy was constructed. | Nested-have and case fixtures must have proper parent, depth, branch scope, and no cross-branch premises. |
| P3 claim statements | Intermediate statements were extracted from tactic text and fell back to the assignment term. This can put proof terms such as `have ... := ...; ?m...` in a claim. Goal/local-context types were not exported. | A claim's statement must equal the Lean local declaration's type, never the assignment proof term. |
| P4 theorem statement context | A regular expression handled only one limited `∀` form, searched only braces for variables, invented assumption names, and discarded binder metadata. It could not map binders to the actual initial fvar context. | Golden statement tests cover implicit/explicit binders, named assumptions, and inaccessible names. |
| P5 internal names | The graph tried to clean `_fvar`/`?m` by string replacement and used the cleaned string as an identity. Pass B exported neither fvar identities nor a reliable user-name mapping. The leak scan only read proof JSON, not every output. | Fvars must be resolved from Lean `Expr.fvar` and `LocalContext`; unmapped ids become explicit partial records, not output names. |
| P6 step segmentation | Pass B emitted every `TacticInfo`, including wrapper and generated syntax. The CLI special-cased a few wrapper names and guessed replacement tactics by searching pretty text; it did not group expansions or parse rewrite lists. | Lean fixture assertions cover meaningful nonempty source ranges, grouped macro parts, and one rewrite node per chain. |
| P7 justification type | `classify_tactic` searched the whole text for automation names and used broad text prefixes. `closed_by_automation` followed that classification even when automation was only nested. | Parent `have` and inner `omega` must retain distinct classifications. |
| P8 declaration refs and auxiliaries | Used constants were reconstructed from strings; new `decl` nodes were bare placeholders rather than references to DAG nodes. `_proof_N` references were not expanded through parent `aux_claims`. | Every non-infrastructure ref must resolve to a DAG declaration; auxiliary references must map through the parent. |
| P9 annotations | Claim/inference fan-out counted ad hoc edges; all inference roles were `main_line`; importance used a constant-offset formula; comments were attached to the nearest line regardless of intervening source. | Tests check graph-derived fan-out/critical path, a documented bounded heuristic, and comment proximity. |
| P10 schema and validation | JSON Schemas allowed almost arbitrary node/edge payloads. Runtime validation used a small inline DAG schema and a few checks, did not validate all output JSON files, and `validate` trusted an existing report. | Every exported JSON file must validate against its versioned schema; v1 input needs a rebuild error. |
| P11 calc/cases | Calc chains and case branches were not represented as claims/scopes. They were treated as ordinary tactics or omitted wrappers. | Three-line mixed-relation calc and nested case fixtures must produce ordered claims and isolated scopes. |

## Validation and tests

The existing V14–V19 code checks only a subset of the stated rules:

- V14 scans proof graphs only, and its `_fvar` scan checks serialized JSON text,
  not each string field in every output.
- V15 checks that a `refs` target occurs in that same proof graph; it does not
  resolve the target against Declaration DAG.
- V16 is absent. V20–V23 are absent.
- V17 and V18 share one `quality_failures` list and do not reject proof terms
  used as claim statements.
- V19 checks only a `final_goal` premise edge; it does not verify cycles in the
  logical inference subgraph, conclusions, reachability, or order-vs-logic.

The pre-change suite passed 27 tests, but it had no schema v1 baseline directory
and no fixtures for the additional cases (m)–(u). Those omissions are tracked as
test gaps, not evidence that the behaviors work.
